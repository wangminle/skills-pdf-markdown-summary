## 一、检查问题与结论

**检查问题**：项目的架构设计是否正确？即：限定输入为标准可编辑 PDF（论文、Word 转出的 PDF 等），输出 PDF 内部已有的结构化数据（标题、图注、字号、位置、段落等），再配一个合理的图表检索器，做成轻量化的 Markdown 生成与图表存图工具。当前代码是否实现了这个目标？

**结论**

1. **架构方向正确。** 限定 born-digital PDF，用 PyMuPDF 读取原生渲染数据，再用几何规则加题注锚点检索图表，并用四态质量门拦截低置信结果。这条路线不需要 GPU，也不需要模型，核心运行依赖只有 `pymupdf`。
2. **目标只实现了一半。** 图表检索与存图链路成熟、可追溯，是当前系统的主体。但"输出内部已有的结构化数据，并据此生成 Markdown"这一半没有闭环，原因是**仓库里有两条互不连通的文本结构化通路**（见第四节）。
3. **需要补一条说明。** PDF 内部原生存在的是渲染数据（文字 span 的坐标、字体、字号、标志位、颜色，以及位图框和矢量路径），不是现成的语义树。段落、阅读顺序、标题层级、图表外框都要靠算法恢复。PDF 书签（outline）和 Tagged PDF 结构树是少数能直接读到的"已有语义"，目前代码没有利用。

> 第一版口头汇报里的"实现度约 80%～85%"和"核心依赖为 PyMuPDF + Pillow + NumPy"这两处表述不准确，已在本报告中撤回并更正，见第六节。

## 三、架构评价

| 设计要素 | 评价 | 说明 |
| --- | --- | --- |
| 限定输入为可编辑 PDF | 合理 | 放弃扫描件，避免引入 OCR 与模型依赖。`--ocr` 现为 `not_implemented`，与定位一致 |
| 读取 PDF 内部结构化渲染数据 | 合理，但落地不完整 | 数据源（`page.get_text("dict")`）选得对；问题在于采集后被分流成两套结构，丢失信息 |

| Markdown 生成 | 主流程闭环，结构还原粗 | 图表内联、公式保护、页眉页脚剔除已有；标题层级、通栏顺序、列表尚未还原 |

## 四、核心发现：文本结构化的双轨割裂

### 4.1 两条通路对比

| 维度 | 轨道 A：`extract_text_with_format` | 轨道 B：`gather_structured_text` |
| --- | --- | --- |
| 位置 | [text_extract.py L487-L649](../../skills/pdf-markdown-summary/scripts/lib/text_extract.py)、[layout_model.py L43-L291](../../skills/pdf-markdown-summary/scripts/lib/layout_model.py) | [text_extract.py L301-L470](../../skills/pdf-markdown-summary/scripts/lib/text_extract.py) |
| 粒度 | 行级 `EnhancedTextUnit`，每行取字符数最多的主 span | 块级，只取块内第一行第一个 span |
| 保留属性 | bbox、字体名、字号、字重、flags、颜色、栏位、缩进 | 仅 `page / text / bbox / is_heading`（[models.py L435-L449](../../skills/pdf-markdown-summary/scripts/lib/models.py)） |
| 分类 | `title_h1/h2/h3`、`caption_figure/table`、`list`、`equation`、`in_figure_text`、`paragraph` | 局部算出 heading/caption/list/body（L419-L426），随即压成 `is_heading` 布尔值 |
| 栏位判定 | 抽样前 5 页，按 x0 直方图找双峰，**依赖 numpy**，缺失时静默退化为单栏 | 全文档一次判定：块中心落在 0.45/0.55 页宽两侧的比例均超 0.3 即判双栏 |
| 落盘 | `images/layout_model.json`：统计、块级 bbox/类型/栏位、前 100 字符样本；逐行字号、字体、颜色不落盘 | `text/gathered_text.json`、`text/markdown_blocks.json` |
| 消费方 | 图表裁剪（版式避让） | Markdown 生成、图表上下文（`figure_contexts.py` 用 `is_heading` 过滤） |

### 4.2 后果

1. 你设想的"输出内部已有的标题、字号、位置、段落等结构化数据"，**内存里有一份（轨道 A），但没有落盘完整版，也没有接入 Markdown**。
2. Markdown 所用的轨道 B 把字号、字体、栏位和 caption/list 分类全部丢掉，导致下面三个具体缺陷。

### 4.3 具体缺陷清单

| 编号 | 缺陷 | 证据 | 严重度 |
| --- | --- | --- | --- |

| F-2 | **双栏页内通栏块排序错误** | [text_extract.py L435](../../skills/pdf-markdown-summary/scripts/lib/text_extract.py) 按块中心 `x_center < 0.5 * page_width` 二分左右栏。CHK-066 用 PyMuPDF 构造的合成样例：顶部通栏块被排到四段左栏正文之后，且报告仍为 `ready` | P1 |
| F-3 | **结构化渲染数据未完整输出** | `layout_model.json` 无逐行字号/字体/颜色；`gathered_text.json` 只有 `is_heading`。与"输出所有结构化渲染数据"的目标有差距 | P2 |
| F-4 | **列表与 caption 判定被丢弃，且规则本身有隐患** | 列表判定用 `startswith(("•","-","*","1.","2.","(1)","(a)"))`：`2.1 Method` 这类非加粗编号行、`-0.5` 这类负数开头的行都会命中。目前因标签未传出而不影响输出，但一旦启用就会暴露 | P2 |
| F-5 | **numpy 缺失时静默退化为单栏** | `layout_model.detect_columns` 在 `ImportError` 时把所有行置为单栏。numpy 在 `requirements.txt` 中是注释掉的可选依赖。这会影响轨道 A 的栏位标注与图表裁剪的双栏处理，且无任何告警 | P2 |
| F-6 | **占位参数说明不足** | `--tables auto/structure` 当前都走截图，`--ocr` 为 `not_implemented`。文档已说明，但 CLI 帮助未说明 | P3 |
| F-7 | **PDF 已有语义未利用** | 未读取 `doc.get_toc()`（书签）。Word 转 PDF 和 LaTeX hyperref 生成的 PDF 通常带书签，可直接给出标题文本、页码和层级。此项属于机会点，不是缺陷 | 机会 |

### 4.4 待验证项（初版提出，2026-11-24 已由 WP-1.1 实测核验）

- 加粗判定只看 `flags & 16`。LaTeX 的 `CMBX*`、`*-Bold` 等字体是否都被 PyMuPDF 置位，需要在 8 份 benchmark 上统计。
- `typical_font_size` 为 6–20pt 范围内全部 span 字号的算术平均，非众数。对表格密集文档的偏移程度未测。
- 书签覆盖率：8 份 benchmark 中带书签的比例、书签文本与正文标题的匹配率，需要先做探测（见 WBS 1.1 / 3.2）。

> **2026-11-24 WP-1.1 实测核验结论**（详见 [架构收敛WP-1.1渲染特征探测简报-20261124.md](../4-analysis/架构收敛WP-1.1渲染特征探测简报-20261124.md)，对应 [[CHK-072]]）：
> 1. **粗体假设被证伪**：8 份 benchmark 中 LaTeX 粗体（`CMBX*`/`CMMIB*`/`CMBSY*`）的 `flags & 16` 置位率为 **100%**；若把版式/标题的结构粗体改为认字体名，反而会把 Kimi-K3 图内 14 个 `DejaVuSans-Bold` 标签误判为 `title_h3` 导致裁剪框回归（即 [[BUG-163]] P1-2）。因此结构判定必须只认标志位，字体名启发式仅限正文行内样式。
> 2. **字号众数须先并簇，且严禁改动版式模型**：LaTeX 10pt 正文在 PyMuPDF 中拆成 `9.96/10.06`，单值众数在 Gemini 上会落到 `8.97pt` 表格字；按 `±0.15pt` 并簇后，7 份文档均值与众数偏差 `< 1.2%`（仅 Gemini 偏低 `4.6%`），且 `11.5pt` 硬门槛拒掉的 324 个非编号短粗体块字号全部小于正文（0 漏判）。若改动 `DocumentLayoutModel.typical_font_size`，会使 Kimi-K3 84 个、Gemini 48 个版式单元重分类。
> 3. **书签命中率极低（后置补漏）**：8 份中 7 份含书签（共 276 条），同页精确唯一命中仅 **9 条（3.3%）**。复核书签落点后仅确认 Kearns 两个真标题曾漏判（[[BUG-171]]），两者随 [[BUG-168]] 恢复；Attention 的同名匹配来自图内标签。探测还发现 [[BUG-169]]（句点编号层级）、[[BUG-170]]（Kimi-K3 单栏误判双栏）与 [[BUG-172]]（目录条目误判标题）。


## 五、图表检索与存图链路评价

### 5.1 已实现的能力

图表检索与存图链路（`core/extract_pdf_assets.py`、`lib/caption_detection.py`、`lib/direction.py`、`lib/extract_figures.py`、`lib/extract_tables.py`、`lib/table_refine.py`、`lib/table_continuation.py`、`lib/assess.py`、`lib/pipeline.py`）是当前代码最完整的部分：

- **题注锚点检索**：支持阿拉伯数字、罗马数字、`S1` 附录、Extended Data、子图 `3a/3(a)` 及中文「图/表」；结合位置、格式、结构、上下文评分过滤正文引用；支持同栏跨块多行合并与全文词形断词还原。
- **多阶段几何与像素精裁**：方向判定（局部对象/表格行证据 + 全局锚点 + 页面位置启发式）→ 邻接题注/版式阻断 → Phase A 文本修剪 → Phase B 位图与矢量对象对齐 → 列感知横向收窄 → Phase D 像素遮罩 autocrop → Figure 短标题/轴标签回补、Table 多行表头/渲染横线/连续行带/表尾脚注回补 → 邻页无题注续表恢复。
- **质量门禁与可追溯落盘**：四态质量验收（`accepted` / `accepted_with_margin` / `review_required` / `rejected`）、全文题注清单对账与缺口补裁、`images/index.json`（含 `final_bbox`、`caption_bbox`、`status`、`pairing_confidence`、`boundary_confidence`、`referenced_in_markdown`、`embed_mode`）、`debug-visual` 三桶线型叠图。
- **Markdown 衔接**：`pdf_to_markdown.py` 仅将 `accepted` / `accepted_with_margin` 资产内联到匹配题注前/后，并用 `final_bbox` 抑制截图框内的散碎正文/表体文字，同时对独立公式碎片区域按栏整块截图或合并为代码块。

### 5.2 存在的结构性压力

1. **外部依赖轻，但规则实现重**：仅运行期 `scripts/` 就有 55 个 Python 文件、339 项功能模块，`table_refine.py` 单文件约 80KB，历史累计修复 160 项 Bug。根因在于 PDF 原生无「图表外框」语义，单靠 Caption 锚点向外推框再层层修剪与回补，每条补丁都容易产生对称反例。
2. **语义 Layout 后端尚未成为默认主链**：`--layout-backend pymupdf4llm`（`lib/backends/pymupdf_layout.py` + `lib/pairing.py` + `lib/pipeline.py`）目前默认 `off`，且仅在规则提取之后作为可选后精修和 shadow 报告运行，尚未取代或前置引导默认单锚点规则链。
3. **重复读取与上下文解耦**：一次 `pdf_to_markdown.py` 执行中，正文阶段调用一次 `gather_structured_text`，随后资产提取阶段再次调用 `try_extract_text`、`gather_structured_text` 与 `extract_text_with_format`，同一份 PDF 被多趟独立解析。（*2026-11-24 WP-1.1 补充实测*：上述文本入口重复扫描合计仅占默认模式总耗时的 6%～18%；真正的重复解析大头在资产提取内部——每页 `get_text("dict")` 以完全相同参数被调用 12～13 次，占总耗时 30%～85%，每页 `get_drawings()` 被调用 4 次，详见 [按页解析调用重复程度](../4-analysis/架构收敛WP-1.1按页解析调用重复程度-20261124.json)。）

## 七、架构收敛目标与范围界定

### 7.1 收敛目标

在不破坏现有图表提取与 Golden 回归的前提下，用**增量并轨**替代推倒重来，达成四个明确目标：

1. **单一渲染事实源（Single Source of Rendering Truth）**：消除 `gather_structured_text` 与 `extract_text_with_format` 的双轨割裂，一次扫描产出包含 `bbox`、字号、字体、字重/flags、颜色、栏位、文档典型指标和（可选）书签信息的统一结构化中间表示，并可完整落盘。
2. **正确的双栏/通栏阅读顺序**：引入页面区域分带（Zone Segmentation），先识别跨栏块（Span-All-Columns）切分上下带，带内再按左栏→右栏排序，彻底解决论文首页标题、作者、通栏摘要和跨栏图注乱序问题。
3. **可信的 Markdown 标题层级、块语义与正文保真**：基于编号深度（含带句点编号 `1. ` / `2.1. `、中文层级、罗马编号）、相对正文字号比例及后置可选 PDF 书签（`doc.get_toc()`）恢复 `H1～H4`，排除目录页条目与长标题误杀；收紧列表/caption 分类，保持行内粗斜体与纯文本分离保真（`rich_text`），对非列表正文行首块级语法做转义并清洗 C0 控制字符。
4. **参数契约透明与依赖行为可观测**：补齐 `--tables`/`--ocr` 的 CLI 帮助说明；去除 `detect_columns` 对 `numpy` 的隐式静默退化（改用纯 Python 标准库实现，留白检测缺依赖显式告警）。

### 7.2 明确不在本轮收敛范围内

为控制改动半径、避免回归爆炸，以下事项**不纳入本次收敛 WBS**：

- **不重写图表精裁主链**（`extract_figures.py` / `extract_tables.py` / `table_refine.py`）：现有图表裁剪经过 8 份 Basic Benchmark 和 841 项回归测试锤炼，本轮仅保证 `DocumentLayoutModel` 接口与行为向后兼容，不触发图表裁剪框漂移。
- **不引入 OCR 或重量级深度学习模型**：继续坚守“标准可编辑 PDF + 纯 CPU 轻量核心”的产品边界。
- **不把 `--tables structure` 强行改为 Markdown 文本表**：表格结构化还原（如 pdfplumber/TableFormer 融合）与当前“图表存图”目标正交，留作后续独立里程碑（参见 `design/4-analysis/MarkItDown与本项目PDF保存能力对比-20261008.md`）。
- **不强推 `pymupdf4llm` 为默认必装依赖**：继续保持 `--layout-backend` 默认 `off`、按需启用。

| **书签（TOC）与目录页噪声误标标题** | 目录页含粗体编号+页码行，或书签含封面/畸形层级 | 按目录标题、点引导线或独立页码列识别目录条目（[[BUG-172]]）。书签回退要求同页文本与排版证据，额外收益待独立评估 |
| **公式区域分组受重排或块元信息影响** | `equation_regions.py` 依赖 `document.blocks` 中的 `paragraph`/`list` 候选块和 `bbox` | 保留 `paragraph` 与被列表分流误判的 `list` 候选及 `meta["bbox"]`，由公式检测器的保守判据排除普通列表（[[BUG-192]]）；每批收尾重跑 `test_issue_regressions_20261006.py` 全部公式回归用例 |
