# PDF 图表提取架构根因复盘与技术路线分析报告

> 日期：2026-07-21
> 范围：本仓库当前正式 Skill、测试、历史调优记录、归档方案与相关开源技术路线
> 核心问题：仅依赖 PDF 的标准化排版结构，能否稳定、完整、清晰地定位并截图所有 Figure/Table；是否必须引入 YOLO、OCR 或多模态大模型
>
> **历史基线说明：**本文中的代码数量、测试数、benchmark 数量、Golden 路径和“当前实现”均是 2026-07-21 快照，不代表 0.6.2 现状。当前实现状态以 `docs/PDF图表提取技术迭代实施方案-20260731.md`、`README.md` 和 `task-list.md` 为准。

## 一、结论先行

### 1. 最重要的判断

**如果目标是“对任意来源、任意学科、任意生成方式的论文或标准排版 PDF，仅依靠标题层级、空格、图注/表注、文字与绘图对象坐标，自动得到 99% 以上完整且纯净的图表截图”，这个目标不能被可靠保证。**

原因不是当前参数还不够好，而是普通 PDF 经常只保存“怎样画这一页”，不保存“哪些绘制指令共同组成 Figure 3”。pypdf 官方文档直接指出普通 PDF 缺少标题、段落、表格等语义层，启发式只能猜测，无法确定；文字甚至可能逐字符绝对定位。[pypdf：Why Text Extraction is hard](https://pypdf.readthedocs.io/en/4.2.0/user/extract-text.html)

Tagged PDF 的确可以包含 Figure、Caption、Table 和阅读顺序，但标签是 PDF 的可选能力，而且大量现存 PDF 并未正确使用。PDF Association 也明确说明 Tagged PDF 是可选特性，并指出多数 PDF 尚未遵循相关最佳实践。[PDF Association：Tagged PDF Q&A](https://pdfa.org/resource/tagged-pdf-q-a/)、[Tagged PDF Best Practice Guide](https://pdfa.org/resource/tagged-pdf-best-practice-guide-syntax/)

因此应把目标拆成三档：

| 目标范围 | 99% 是否有机会 | 前提 |
| --- | --- | --- |
| 固定出版社、固定模板、born-digital、caption 规范 | 有机会 | 独立标注测试集、允许按模板适配、低置信样本回退 |
| 主流英文/中文论文，来源较多但仍限于学术 PDF | 可以追求很高自动通过率，但不应先承诺 99% | 规则与视觉布局检测融合，独立 benchmark，明确失败输出 |
| 任意“看起来排版标准”的 PDF，要求截图完整且无正文污染 | 不能靠结构启发式保证 99% | 需要学习型布局模型、OCR/视觉回退和人工复核共同兜底 |

注意本报告出现了两种口径的“99%”，分母不同，不可混用：本节指的是“所有输入都强制自动截图且 99% 正确”，这一目标在开放世界不可保证；第六、七节讨论的 99% 指的是**自动接受子集**的准确率，即已把低置信样本移入 review_required 之后的条件准确率。后者可以作为工程目标，但它并不等于前者被达成。

### 2. 是否必须安装 YOLO

**不必须。** YOLO 只是布局目标检测的一种实现。可替代方案包括：

- PyMuPDF4LLM 当前的 Layout 模块：CPU-only、GNN 路线，可输出带类别的 page boxes；
- Docling：使用专门的布局模型和 TableFormer，布局模型为 RT-DETR 系；
- PaddleOCR PP-StructureV3 / PP-DocLayout：检测器也是独立布局模型，不等于 YOLO；
- GROBID / PDFFigures2：针对学术论文的结构与规则/统计模型；
- 自己训练或微调的轻量检测器。

DocLayout-YOLO 是值得作为候选后端评测的强基线，但不应写死为唯一架构。其官方结果在 DocLayNet 上报告的 mAP 为 79.7，而不是 99%，也说明“装了 YOLO”不等于问题自动解决。[DocLayout-YOLO 官方仓库](https://github.com/opendatalab/DocLayout-YOLO)

### 3. 是否必须具备多模态大模型

**不必须，也不建议把通用多模态大模型作为每页必经主链。**

图表边界定位首先是版面目标检测和几何融合问题；一个小型布局检测模型通常比生成式 VLM 更便宜、可复现、可校准。多模态模型更适合：

- 处理低置信页面；
- 判断某段文字是图内标题还是正文；
- 检查截图是否截断；
- 理解图表内容并生成摘要；
- 处理扫描件、复杂公式、图中 OCR 或图表语义。

PaddleOCR-VL 使用 0.9B VLM 支持 109 种语言和复杂元素识别，证明 VLM 可以做强回退，但它仍是模型依赖，不属于“轻量纯 Python 核心”。[PaddleOCR-VL 论文](https://arxiv.org/abs/2510.14528)

### 4. 能否做成依赖尽可能少的 Python 工具

**可以，但必须改变产品承诺：轻量版负责高置信场景，不负责掩盖不确定性。**

推荐产品形态不是“一个万能 robust 参数”，而是：

1. **Lite 核心**：PyMuPDF，处理有文本层、caption 规范、对象边界清晰的 PDF；
2. **CPU Layout 增强**：可选 PyMuPDF4LLM Layout 或 Docling layout；
3. **Heavy 增强**：可选 DocLayout-YOLO、PP-StructureV3、OCR/VLM；
4. **人工复核接口**：低置信时输出 page、caption bbox、候选 bbox、debug overlay，不静默导出错误截图。

这样可以保持默认安装轻量，又不把开放世界问题假装成已解决。

## 三、当前仓库真正实现了什么

### 1. 图表定位主链

当前 Figure/Table 的主要数据流是：

1. 用正则在文本层找 Figure/Table caption；
2. 对 caption 候选做位置、格式、结构、上下文评分；
3. 判断图表在 caption 上方还是下方；
4. 从 caption 向一个方向建立固定高度 baseline 矩形；
5. 用相邻 caption、正文块、标题块限制 baseline；
6. Phase A 文本裁剪；
7. Phase B 图像/矢量对象对齐；
8. X 方向列感知收窄；
9. layout blocker 调整；
10. 像素 autocrop；
11. Figure 标题/对象回补或 Table 表头/末行/宽度回补；
12. 用墨迹、面积、高度、正文污染等指标验收或回退；
13. 渲染 final clip 为 PNG。

以上是简化描述，实施时应以代码为准：没有 Phase C，像素 autocrop 直接命名为 Phase D；第 9 步对应的是 `adjust_clip_with_layout`，不是独立的 layout blocker 环节；图内标题回补在 baseline 阶段也会发生一次，不只在 autocrop 之后；此外还有 global anchor 预计算、caption 索引预扫描、`refine_clip_to_table_band`、`expand_clip_to_rendered_horizontal_rule` 等步骤未列入上表。

这个流程的调试能力是当前项目最成熟的部分：baseline、phase_a、phase_b、phase_d、final 均可画线，错误可以定位到具体阶段。

### 2. Markdown 产品层仍未闭环

当前 PDF-to-Markdown 入口存在几个与产品描述不一致的地方：

- tables=auto、screenshot、structure 在主流程里没有不同实现；只要不是 off，最终都走截图提取；
- pdfplumber 的表格函数存在于 pdf_backend.py，但没有接入 Markdown 的 structure 分支；
- OCR 参数会写入报告，但状态明确是 not_implemented；
- 图表没有插回原 caption 位置，而是统一追加到 Markdown 末尾“提取资产”章节；
- AttachmentRecord 和 index.json 没有保存 final crop bbox，也没有保存候选置信度、采用阶段和失败原因。

因此目前更准确的定位是：**基于 caption 的图表截图工具 + 文本转 Markdown 雏形**，而不是已经完成的通用 PDF-to-Markdown 引擎。

### 3. 当前方案值得保留的资产

以下工作不应推倒重来：

- caption 标识符解析覆盖数字、Roman、S-prefix、Extended Data、中文图表标签；
- caption/reference 区分和多行 caption 合并；
- PyMuPDF 对文字、图像、矢量对象和渲染的统一坐标层；
- Figure/Table 分流后的专用 refinement；
- debug visual 和结构化日志；
- 真实 PDF 的大量正负例知识；
- caption 与正文 mention 的上下文关联；
- 相对路径、索引、输出清理和 CLI 框架。

这些都适合成为新架构的“候选生成、边界精修和可解释调试层”。

## 四、为什么数月调参仍不能稳定到 99%

### 根因一：输入通常没有你要恢复的语义边界

一张人眼看到的图，可能在 PDF 内部表现为：

- 一个完整 raster image；
- 数百条 path、rect、line、curve；
- 多个小图像与独立文本标签叠加；
- 页面背景、图例、坐标轴、标题分别位于不同 content stream；
- Form XObject 被多次复用；
- 图主体是图片，但轴标题和子图标号是页面文本；
- 表格完全由文字对齐构成，没有任何线；
- 视觉横线被字体 glyph 或细矩形画出，get_drawings 未必按预期返回。

PyMuPDF 官方说明也指出，矢量图形不是 PDF image，不能像嵌入图片一样直接提取，只能读取为基础绘图命令。[PyMuPDF FAQ](https://pymupdf.readthedocs.io/en/latest/faq/index.html)

所以“检测到图片对象 bbox”只对部分论文有效；“合并所有 drawing bbox”又容易吞进公式、分隔线和相邻图。

### 根因二：caption 是强锚点，但不是图表边界

caption 能高效回答“这里附近可能有 Figure 3”，却不能唯一回答：

- 图在上还是在下；
- caption 属于上方哪个对象；
- 图内标题是否属于图；
- 图脚、脚注、panel label 是否属于图；
- 两张并排图是否共享 caption；
- 表格是否跨页；
- caption 与图之间是否插入正文；
- 本页出现的是 caption 还是正文引用。

当前代码把 caption 继续扩展成唯一主锚点，导致后续所有阶段都在修正一个可能一开始就选错的矩形。

### 根因三：问题被限制成“单页、单矩形、上或下”

当前核心输出只能表达一个 axis-aligned rectangle。它无法自然表达：

- L 形或不规则图；
- 同一 caption 对应多个分离 panel；
- 三张贴边图共享边界；
- 跨页表格；
- 图表 footnote 与主体分离；
- caption 在侧边；
- 旋转 caption。

PDFFigures2 也明确列出 L 形图、三张相邻共享边界、旋转文字、同一行多个 caption 等持续失败的边界情况；其 API 同样受单 bbox 假设约束。[PDFFigures2 官方仓库：Common Sources of Errors / Unhandled Edge Cases](https://github.com/allenai/pdffigures2)

### 根因四：每条修复规则都存在对称反例

仓库自己的最终复盘已经列出 25 条策略冲突（见 `docs/1-archive/Basic-Benchmark图表细致排查记录-20260618-0621.md` 的“当前策略冲突清单”）。例如：

- far-side 正文检测会误伤图内标题；
- 图内标题回补会吞入章节标题；
- 对象面积阈值会漏掉小对象密集图；
- 放宽对象阈值会引入噪声；
- Table 末行回补会恢复数据行，也会恢复数字正文；
- 双栏收窄能去正文，也会把伪双栏页面裁成窄条；
- 低比例软接受能保住短表，也会保留上游截断结果。

这不是实现者不够细心，而是同一组局部几何特征可对应不同语义。继续增加守卫会提高已知样本通过率，却会扩大规则相互作用空间。

### 根因五：训练集、调参集和验收集高度重合

Basic Benchmark 的 7 份 PDF 被反复用于：

- 发现错误；
- 设计规则；
- 调整阈值；
- 编写正例/负例单元测试；
- 最终目视验收。

这是一套优秀的回归集，但已经不是独立泛化测试集。DeepSeek V4 作为后续新样本时，立即出现 Table 方向被上一张表吸走、真实 Table 6 漏检、Table 8 混入正文、Table 12 截断等新问题，正好说明已知 benchmark 收口不等于总体分布收口。

### 根因六：现在还没有“99%”可计算指标

Golden 测试当前只会因为三类问题判定失败：

- Figure/Table 数量与预期不符；
- 预期 ID 缺失；
- 截图文件不存在。

另有两类只写入 message、不置 `passed=False`，因此实际上不构成约束：

- caption 是否非空；
- 与 golden 签名 `(type, id, page, continued)` 的差集，以及多出的 ID。

它完全不比较：

- 预测 bbox 与人工 bbox；
- 图表主体覆盖率；
- 截图正文污染率；
- caption 配对是否正确；
- 图内标题/脚注是否按产品规范保留；
- 多 panel 或跨页关系。

更关键的是 final bbox 没有进入 AttachmentRecord/index.json，所以当前产物本身不能自动做 IoU 回归。**在没有 geometry ground truth 与指标之前，“99%”只是主观感受，不是工程目标。**

## 五、外部最佳实践带来的启示

### 1. 纯规则学术方案的上限：PDFFigures2

PDFFigures2 与本项目思路非常相似：找 caption、分类 BodyText/Other、生成多个候选区域、打分、避免重叠、渲染截图。论文在 CS-150 上报告 P=0.980、R=0.961、F1=0.970；在更大、更难的 CS-Large 上下降到 P=0.936、R=0.897、F1=0.916。[PDFFigures 2.0 论文](https://ai2-website.s3.amazonaws.com/publications/pdf2.0.pdf)

这组结果很有价值：**在受限的计算机科学论文域，优秀规则/统计系统可以接近 97% F1；分布扩大后仍会明显下降。** 它不支持开放世界 99% 假设。

### 2. 通用解析的主流已经是“多源、多阶段”

OmniDocBench 当前发布版（v1.6）覆盖 1,651 页、10 类文档、5 类版式、5 类语言，并提供布局、阅读顺序、表格等细粒度标注；需要注意 CVPR 2025 论文描述的是 v1.0，规模为 981 页、9 类文档、4 类版式、3 类语言，引用时不要混用两版数字。论文结论是 pipeline 和端到端 VLM 各有强弱，文档类型扩大后性能显著分化；这也是为什么现代系统不再只依赖 PDF 文本结构。[OmniDocBench 论文（对应 v1.0）](https://openaccess.thecvf.com/content/CVPR2025/html/Ouyang_OmniDocBench_Benchmarking_Diverse_PDF_Document_Parsing_with_Comprehensive_Annotations_CVPR_2025_paper.html)、[OmniDocBench 数据集（v1.6）](https://huggingface.co/datasets/opendatalab/OmniDocBench)

MinerU 的论文也明确采用布局检测、公式/表格模型、PDF 预处理和后处理规则的组合，并承认文档多样性使开源方案难以稳定输出高质量结果。[MinerU 论文](https://arxiv.org/abs/2409.18839)

### 3. 值得优先实测的基础库

| 候选 | 是否需要生成式 VLM | 部署重量 | 对本项目的价值 | 主要限制 |
| --- | --- | --- | --- | --- |
| PyMuPDF 原生 | 否 | 最轻 | 渲染、文字/图像/绘图对象、find_tables | 缺语义，无法独立解决图边界 |
| PyMuPDF4LLM Layout | 否，CPU-only GNN | 中等 | page_boxes 含 class 和 bbox；与现有 PyMuPDF 最接近 | 新组件，必须在本项目语料上验证；PyMuPDF 许可证需评估 |
| PDFFigures2 | 否 | 中等，Scala/JVM | 学术论文专用强基线、caption-region pairing 设计成熟 | 非 Python、域偏 CS、已知边界情况多 |
| GROBID | 否 | 中到重，Java/服务 | 学术结构、section/caption/figure-table 坐标，可作为语义锚点 | 不专注像素级干净截图，服务部署较重 |
| Docling | 否；VLM 为可选 | 重，PyTorch + 模型 | 布局、表格、OCR、阅读顺序和 Markdown 一体化 | 依赖/模型较多，仍会失败，需 adapter |
| DocLayout-YOLO | 否 | 重，PyTorch + 权重 | figure/table/caption 粗 bbox，速度高 | 只是 detector；类别映射、caption 配对和精修仍需本项目完成 |
| PP-StructureV3 | 否，传统多模型 pipeline | 重，Paddle + 多模型 | 20 类布局、多语言 OCR、表格/公式/Markdown | 安装和模型体积较大 |
| PaddleOCR-VL | 是，0.9B | 很重 | 扫描件、复杂表格/公式/图表识别与低置信回退 | 成本、速度、显存、结果可复现性 |

PyMuPDF4LLM 的当前 API 可在 page_chunks 输出中返回 page_boxes，并以 class 标识布局框；官方还说明 Layout 为 CPU-only、无需 GPU。最新版已把 Layout 内置进主包，`import pymupdf4llm` 即自动激活，不再需要单独安装和对齐版本；同时它提供插件式 OCR，Tesseract / RapidOCR / PaddleOCR 任一存在即自动只对需要 OCR 的区域处理。因此 Phase 2 评测这一个依赖，有可能同时覆盖 Phase 3 中的 OCR 部分，两个阶段可以视评测结果合并前移。这是最符合“尽量保持 Python 和较少依赖”的第一候选。[PyMuPDF4LLM API](https://pymupdf.readthedocs.io/en/latest/pymupdf4llm/api.html)、[PyMuPDF Layout 教程](https://pymupdf.io/blog/pymupdf-layout-tutorial)

Docling 安装简单，但其模型依赖 PyTorch；OCR、VLM 等通过 extras 扩展，适合做可选后端而非最小核心。[Docling 安装文档](https://docling-project.github.io/docling/getting_started/installation/)、[Docling Model Catalog](https://docling-project.github.io/docling/usage/model_catalog/)

PP-StructureV3 的布局模型覆盖 title、text、table、image、figure/table title、chart、formula 等类别，并包含阅读顺序和 Markdown 输出能力，适合中文、扫描件与复杂表格路径。[PP-StructureV3 官方文档](https://www.paddleocr.ai/latest/en/version3.x/pipeline_usage/PP-StructureV3.html)

### 4. 许可证风险

仓库自身使用 Apache License 2.0，但 PyMuPDF 官方当前说明其开源许可为 AGPL，并提供商业许可。由于 Lite 核心目前唯一的关键依赖就是 PyMuPDF，“是否把 PyMuPDF 隔离为可替换后端”应作为 Phase 0 的架构约束一并决定，而不是留到准备分发时才处理。是否会影响你的分发、桌面应用或 SaaS 形态需要结合实际发布方式进行法务确认；本报告不作法律结论。[PyMuPDF 官方许可说明](https://pymupdf.io/pymupdf)

## 六、推荐的新架构：从“caption 截窗”改为“页面场景图 + 多证据融合”

### 1. 目标数据模型先改

每个 Figure/Table 不应只保存 file、id、page，而应保存：

- asset_id、type、subtype；
- page_start、page_end；
- caption_text、caption_bbox；
- content_bboxes：允许多个矩形；
- render_bbox：最终用于截图的矩形；
- source_signals：tag、embedded_image、drawing、table_finder、layout_model、caption；
- pairing_confidence、boundary_confidence、quality_confidence；
- selected_candidate、rejected_candidates；
- processing_backend、模型版本、阈值版本；
- warnings：possible_truncation、possible_pollution、cross_page、ambiguous_pairing；
- debug artifacts。

只有先保存 bbox 和置信度，后续才能做回归、复核和模型融合。

### 2. 候选生成不再只有 caption

同一页并行生成多类候选：

1. Tagged PDF 的 Figure/Table/Caption；
2. PyMuPDF image blocks；
3. PyMuPDF drawings 的连通组件；
4. PyMuPDF page.find_tables()；
5. caption anchors；
6. 可选 PyMuPDF4LLM Layout / Docling / YOLO 检测框；
7. OCR 文本和版面框（仅扫描件或文本层异常时）。

caption 仍是强信号，但不再负责独自生成最终框。

### 3. 建立 Figure/Table/Caption 配对图

将页面建模为节点和边：

- 节点：caption、figure candidate、table candidate、title、paragraph、header/footer；
- 边：距离、方向、列重叠、编号连续性、模型类别一致性、对象覆盖、阅读顺序；
- 约束：一个 caption 通常配一个 asset group，候选之间不能无解释重叠；
- 求解：二分匹配、最小代价流或小规模图搜索。

这比“对每个 caption 独立判断 above/below”更能处理同页多图表互相抢占。

但要清楚它解决的不是根因四：边权（距离、方向、列重叠、编号连续性）同样是需要人工确定的参数，配对图只是把阈值从散落的 if 分支搬进统一的代价函数，让冲突可见、可整体求解，并不自动消除调参空间。真正约束这些参数的是 Phase 0 建立的 ground truth 与指标，而不是模型形式本身。

### 4. 检测模型只负责粗框，现有规则负责精修

布局模型输出通常是 coarse bbox。现有项目的价值应放在：

- PDF 坐标与渲染坐标对齐；
- caption 边界剔除；
- 图内标题、panel label、axis label 回补；
- Table 表头、末行、横线和 footnote 策略；
- 像素级白边裁剪；
- 基于 PDF 对象的边缘 snap；
- debug 与质量验收。

即采用：

**模型找区域 → PDF 对象精修 → 像素精修 → 质量打分 → 必要时回退**

而不是：

**caption 猜大窗口 → 依次删除/回补 → 多次回退**

### 5. 不确定性必须成为正式输出

推荐三种结果：

- accepted：高置信自动导出；
- accepted_with_margin：主体完整，但保留额外空白或少量邻近文字；
- review_required：配对、边界或跨页关系不确定，输出候选与整页 debug，不伪装成功。

如果产品允许 1% 左右样本进入 review_required，那么“自动接受结果的准确率”达到 99% 比“所有输入都强制自动截图且 99% 正确”现实得多。

## 七、重新定义 99% 和 benchmark

### 1. 至少分开四个指标

| 指标 | 建议定义 |
| --- | --- |
| Caption detection | caption precision / recall / F1 |
| Asset detection | 每个真实 Figure/Table 是否找到，precision / recall / F1 |
| Pairing | caption 与正确 asset group 的配对准确率 |
| Localization | bbox IoU、主体覆盖率、截图纯净率 |

对“截图完整且干净”，单纯 IoU 不够。建议同时记录：

- content coverage = GT 与预测交集 / GT 面积；
- crop purity = GT 与预测交集 / 预测面积；
- strict success：coverage ≥ 0.98 且 purity ≥ 0.95，caption 配对正确；
- safe success：coverage ≥ 0.995，允许 purity 较低，即宁可多留白不截断；
- human score：完整、污染、错误配对、不可判定四类。

具体阈值应由产品决定，而不是直接沿用上述示例。

### 2. ground truth 必须允许多 bbox 与歧义

标注格式应支持：

- 一个 asset 多个 content bbox；
- 跨页；
- caption bbox；
- footnote 是否属于截图；
- 图内标题是否必须包含；
- ambiguity flag；
- 可接受边界范围，而非只有一个“唯一正确像素框”。

### 3. 重新拆分数据集

建议最少建立：

- dev：现有 7+1 份 PDF，可继续用于快速调试；
- test-in-domain：不同论文、相同主要来源；
- test-cross-publisher：此前从未出现的出版社/模板；
- test-hard：扫描件、旋转、跨页、同页多图、无边框表、同一行多个 caption；
- holdout：冻结，调参期间不可查看。

应按“文档/出版社”切分，而不是把同一文档的不同页随机分到训练和测试。

### 4. 统计口径

即使所有样本都同分布，在零失败情况下，要让 99% 成功率的单侧 95% 置信下界超过 99%，也需要约 299 个独立资产；一旦观察到 1 次失败，所需样本量升到约 470 个。而且这个计算依赖样本独立同分布，该假设与上面提到的模板分布漂移本身冲突，因此 299 是下限而非目标。实际建议至少标注数千个资产，并按来源报告分层结果，而不是只给一个总平均值。

## 八、建议实施路线

### Phase 0：停止继续调“万能 robust”

时间建议：1 周。

- 冻结当前 robust，标记为 legacy-heuristic；
- 给 AttachmentRecord/index.json 增加 bbox、confidence、selected stage、warnings；
- 修正 Golden 测试，使其读取 tests/results 下的产物；
- 建立 50–100 个资产的 bbox 标注试验集（仅用于打通指标管道，样本量不足以支撑任何准确率结论，见第七节统计口径）；
- 明确 caption 是否包含在截图、footnote 是否包含、跨页如何输出。

退出条件：可以自动计算 detection、pairing、coverage、purity。注意此时还不能用这批数据判定“哪个方案更好”，那需要标注量达到第七节要求的量级。

### Phase 1：轻量候选融合

时间建议：2–3 周。

本阶段的设计依赖 Phase 0 的指标结果，有可能被否决或大幅调整；不要在 Phase 0 交付前就把它当成既定方案开工。

- 增加 Tagged PDF 检测；
- 接入 PyMuPDF page.find_tables()，优先提供 Table bbox；
- 对单一大 image block 建立高置信 Figure 快路径；
- 将 caption、image、drawing、table candidates 放入统一数据模型；
- 用一对一配对代替逐 caption 独立 above/below；
- 现有 refinement 改为对候选框精修。

退出条件：Lite 模式在独立 born-digital 学术测试集上显著优于当前 robust，且规则数不继续爆炸。

### Phase 2：评测 CPU Layout 后端

时间建议：2 周。

同时做 adapter，不先决定赢家：

- backend=pymupdf-layout；
- backend=docling；
- backend=grobid（主要评估 caption/section/coords）；
- baseline=pdffigures2（离线对照）。

比较：

- Figure/Table recall；
- bbox coverage/purity；
- 每页时间；
- 峰值内存；
- 安装体积；
- macOS arm64 / Windows / Linux 可用性；
- 许可证。

如果 PyMuPDF4LLM Layout 在论文域表现足够好，它最可能成为 Balanced 模式默认后端。

### Phase 3：只对困难页启用重模型

时间建议：3–5 周。

- 插件式接入 DocLayout-YOLO 或 PP-DocLayout；
- scanned/text-layer-bad 页面接 OCR；
- 只有 pairing/boundary 低置信时调用 PaddleOCR-VL 或其他 VLM；
- VLM 只返回结构化判断和候选选择，不直接无约束生成文件；
- 所有模型输出仍交给 PyMuPDF 做最终坐标截图。

退出条件：困难集 recall 提升，且普通 PDF 的速度/依赖不受影响。

### Phase 4：产品级置信与人工复核

- 输出 contact sheet、候选框和一键选择；
- 保存人工修正为新 ground truth；
- 统计 review_required 比例；
- 以“高置信自动接受准确率 + 人工复核率 + 总召回率”作为正式 KPI。

## 九、建议立即停止或降级的做法

1. 不再以新增某个 pt、宽度比、字符数阈值作为主要路线；
2. 不再用同一批 7 个 PDF 同时调参与证明准确率；
3. 不再把数量正确、文件存在称为截图准确；
4. 不再让 OCR 和 tables=structure 以可选参数形式存在但实际 no-op；应明确标记未实现或真正接线；
5. 不再把所有资产统一追加到 Markdown 末尾；应基于 page + caption bbox 插回阅读顺序；
6. 不再丢弃 final bbox、置信度和候选来源；
7. 不再强制每个 caption 只输出一个单页矩形；
8. 不再假设模型一定需要 GPU；先评测 CPU Layout；
9. 不再把 VLM 当成“装上就达到 99%”的替代品。

## 十、最终回答

### “通过标准化结构找到准确的图的位置”是否可以达成

**在有可靠标签、固定模板或受限论文域内可以；对任意看起来标准的 PDF，不能仅靠结构启发式保证 99%。**

### 是否还需要更好的基础库

**需要。** 第一优先应评测 PyMuPDF4LLM Layout 和 PyMuPDF 原生 find_tables；第二优先是 Docling/GROBID；困难页再评测 DocLayout-YOLO 或 PP-StructureV3。PDFFigures2 应作为学术论文专用基线和架构参考。

### 是否能做成轻量 Python 工具

**能。** 但轻量版应是高置信提取器，并提供明确的 review_required；通用高准确模式通过 extras 安装模型后端。不要让所有用户默认安装完整 OCR/VLM 栈。

### 是否必须安装 YOLO

**不必须。** 需要的是“可替换的布局检测能力”，不是特定 YOLO 实现。

### 是否必须具备多模态大模型

**不必须。** VLM 应作为扫描件、复杂元素和低置信页的可选回退或质检器；Figure/Table 粗定位可由更小、更确定的布局模型完成。

### 对当前仓库的总评价

这个仓库不是失败了。它已经把“caption 驱动裁剪为什么难”研究得非常充分，并积累了难得的调试、负例和精修资产。真正需要改变的是项目的中心假设：

> 从“找到更完美的一组规则参数”，转向“用多种独立证据生成候选、用模型给出粗语义边界、用 PDF 几何做精修、用置信度承认不确定性”。

继续在现有主链上增加守卫，能够让已知样本越来越好，却很难让未知分布达到 99%。把现有代码降级为可解释的 refinement 层，再加入可插拔 layout backend 和正式 bbox benchmark，才是最有机会把项目做成稳定产品的路线。
